# ADR 0028 — Patient records, named-doctor sharing and care retention

Date: 2026-11-05. Status: accepted for local implementation.

## Record ownership and uploads

Patient-origin records are separate from immutable clinic-authored documents and ordered test results. They belong to a patient in one tenant; current consent and verified-number/guardian/merged-history ownership protect every patient read/write/file action. The web My records page provides prescription, lab, imaging, discharge and other categories, dates/notes, links to the same patient's appointments or signed test orders, editing and bounded cursor pagination. Linking an order does not submit a result or change its clinical status; use Tests for that workflow. Referenced visits/orders must belong to the same live patient, including merged history.

Reserve a record with a client UUID and encrypted title/note, then upload its raw file. Retrying the original metadata/body returns the same record. Raw input SHA-256 binds the file attempt even when PDF rebuilding changes stored bytes; a ready file cannot be replaced. Competing uploads serialize on the row. Storage writes use unpredictable keys; uncertain commits recheck the committed pointer before cleanup. File downloads re-hash stored content and use generic filenames, authenticated requests, no-store/nosniff/sandbox headers and session-scoped revocable blob URLs. No titles, clinical notes, original filenames or record-share tokens enter URLs, queue jobs or audit metadata.

Reuse the clinic's bounded PDF/still-image acceptance and PDF rebuild pipeline. PDFs are rebuilt before storage; SVG, HTML, animation, malformed/polyglot files and disallowed/oversized media are rejected. Select up to ten files per web batch. Interrupted batches retry their original UUIDs; already saved files are recovered rather than duplicated. Definitive refusals permit corrections, and the user can stop retrying and inspect saved/unfinished records. Unfinished reservations expire after 24 hours.

For multi-page photos, the browser sequentially flattens/resizes selected images to JPEG (maximum 1536 pixels on a side), then sends two to ten pages for PDF assembly. The server accepts only flattened JPEG page inputs, checks base64/type/structure/dimensions, caps total bytes at the smaller of the clinic limit or 10 MB, and caps total pixels at 20 million. JPEG embedding avoids decoding untrusted PNG streams on the server. There is at most one photo assembly per organisation and two per API process. The assembled PDF then passes through the existing rebuild/size checks. Pass an owned Uint8Array into pdf-lib's JPEG embedder: its DataView ignores a pooled Node Buffer's byte offset. Files are supplied by the user; no generative imagery is involved.

## Sharing and clinician use

A patient chooses a named active clinic doctor and a one-to-168-hour lifetime. An immutable share UUID recovers the same recipient/expiry/token after an uncertain response. At most ten shares per record may be active. Tokens are random, stored hashed for lookup and encrypted for the owner's recovery, and placed only in a URL fragment. The landing page requires the named doctor's active session in the correct clinic; forwarding a link does not authorize another account. It removes the fragment after authorized resolution. A signed-out doctor can sign in in another tab and reload the original page without putting a token into a sign-in query string. Anonymous/external-doctor sharing is not part of this increment.

An explicit share opens only this file and its metadata. It does not open the rest of an own-patients chart or let another clinic/role read it. Doctor record lists include only active authorized shares or records that doctor previously used. Current grantor consent is rechecked for unused shares. Portal consent withdrawal revokes grants for the account/owned family; used clinical copies remain available to their treating doctor. Revocation/expiry prevents future link access, but cannot recall previously downloaded copies.

Opening is not reviewing, and reviewing is not recording care use. Review/use actions require the displayed record revision. A doctor explicitly records use from their checked-in, in-consultation or completed visit for this same patient. That creates an append-only use row. A database trigger stamps first use and thereafter freezes file bytes, metadata, links and revision. The original patient record/IDs remain intact. Doctors should record use whenever they rely on an uploaded document during care; the system cannot infer decisions made outside it. Other clinic roles cannot read or review these clinical files.

## Deletion, hiding and recovery

Unused deletion immediately hides the record, revokes its links and enters a durable deleting state. The API maintenance sweep runs every 30 seconds, claims/fences bounded work under tenant RLS, and removes active-store bytes before clearing encrypted details and fingerprints. Storage failure leaves deletion pending with a delayed retry; a crashed/expired lease is reclaimable. A crash after bytes are removed is safe because file deletion is idempotent. Completed deletion keeps a minimal immutable tombstone/audit, not the file/title/note/clinical links. Expired unfinished uploads follow the same cleanup path. This does not promise erasure of every infrastructure backup; production storage/retention controls remain separate work.

A record used in care is never sent to the deletion sweep. Patient removal hides it and revokes share links while the treating doctor's clinical copy remains. A patient may restore its visibility; this never reactivates old shares. Database use/file/state guards and row locks serialize use against deletion, preventing a file already recorded as used from being purged. Current-family, merged-history, grantor, clinician and tenant checks are independent of knowing an object ID.

## Boundaries and validation

No automatic WhatsApp notice, public bearer download, external messaging, native UI/build, production S3/scanner deployment or legal retention-period decision is added here. Cloud DSC and AI remain deferred. Local storage is the existing FileStore adapter; production object storage, scanning/backup policy, durable orphan inventory and release acceptance remain open in the wider plan. No PR, deployment or real provider send was performed.

Integration coverage includes idempotent reservation/file recovery, encrypted metadata, family/tenant/consent boundaries, doctor identity/expiry/revocation, retained use and immutable history, purge failure/retry, use/delete races, combined JPEG pages/PDF integrity, stale review versions, treating-visit restrictions, file-only grants under restricted charts, pagination and unfinished-upload expiry. Browser coverage exercises combined upload → named-doctor link → review/use → patient hide/restore at 390px and 1280px, plus lost-response raw-upload recovery and unused deletion.

Validation: all 45 migrations applied to disposable databases, including grantor backfill; 72 affected API integration tests across five suites passed; all 52 scoped web/API/worker/shared checks passed; all 72 web browser tests passed. The new browser cases cover 390px/1280px combined upload/share/clinical-use/hide/restore and interrupted raw-upload recovery/deletion. Formatting and diff checks passed. These are local synthetic checks, not production storage/scanner, provider, backup or clinic acceptance.
