# ADR 0024: Prepaid in-person booking with provider-confirmed reservation release

- Status: Accepted; implemented locally, disabled until a sandbox pilot
- Date: 2026-11-05

## Decision

Add prepaid **in-person web bookings** using the existing Cashfree checkout, original-order recovery, signed callbacks and receipt processor. Video/audio/chat booking, identity checks, telemedicine consent and native checkout remain separate work. `CASHFREE_PREPAID_BOOKING_ENABLED=false` gates new reservations on the API; the main Cashfree integration and the clinic merchant configuration must also be available. Supporting clients opt in to prepaid booking options with `?prepaid=true`; older mobile clients retain their existing options.

A patient submits an immutable UUID and booking choices, never an amount. Under the existing patient/doctor/day locks, one transaction checks consents, family ownership, slot availability and booking limits; reserves a pending appointment; creates a frozen standard-fee bill and line; reserves the original Cashfree order; and inserts `cashfree_bookings`. Quote fees are ₹1–₹1,00,000, from the server's consultation type, with no discount/follow-up selection in this increment. Capture the clinic's automatic-confirmation setting at reservation time. Hold identities and a keyed digest of the request support retries without retaining another copy of the clinical reason. Dependants use the account's verified phone for checkout.

Only after commit may the existing payment adapter call Cashfree. Unknown responses still return the recoverable reservation ID. Retrying uses the same order, provider idempotency key and fee snapshot. A different UUID cannot take an already reserved slot or bypass active-booking limits. The ordinary free-booking endpoint rejects prepaid types. Unpaid reservations cannot be manually confirmed, checked in, marked no-show or moved. Quote lines and totals remain immutable, and replacement orders/counter payments are blocked. Prepaid appointments cannot be rescheduled in this increment; cancellation and an explicit clinic refund are separate actions.

Verified success posts the existing numbered receipt and advances the reservation in the same transaction. If automatic confirmation was selected, a future pending appointment becomes confirmed and its existing opted-in notification trigger runs. Otherwise the paid appointment remains pending for the clinic to approve. Browser checkout results never confirm either payment or booking. A success arriving after release or after the slot starts posts the verified receipt but marks the reservation for review; it never restores the slot. Patient and bill screens show the review, and the audit trail records it. Refunds use the existing explicit admin workflow; cancellation does not automatically refund.

Checkout lasts 30 minutes; prepaid slots must be at least 35 minutes away as well as satisfy the clinic's ordinary cutoff. The API sweeps expired reservations every 30 seconds, with tenant-scoped durable claims and bounded batches. Check current provider status before attempting termination, then verify terminal order status and successful/pending payment attempts. Only verified EXPIRED/TERMINATED closure without an unresolved payment releases the appointment. Local expiry, transport failure, missing/unknown provider order and TERMINATION_REQUESTED do **not** prove safe release. Such holds remain reserved and retry after the database lease, including after a restart. Patient/staff checks use the same processor. Pausing new reservations does not stop existing callbacks or cleanup; keep the main integration and original account available.

## Consequences and validation

`cashfree_bookings` has tenant RLS, restricted internal writes, immutable source bindings and guarded transitions. Appointment, bill-line and payment triggers prevent staff/database application-role bypasses. Unpaid holds do not become patient no-shows. Portal reads check current family/history ownership and consents. Queue payloads and additional provider APIs are not introduced; the API's existing verified processor owns the expiry sweep, and external calls remain outside database transactions.

Local validation covers concurrent IDs, exact quote snapshots, consent/ownership and free-flow bypasses, dependant accounts, unknown creation recovery, duplicate signed callbacks, manual approval, uncertain closure, late success, no-show exclusion and unchanged existing booking/payment/refund behavior. Browser tests cover reserve → checkout link → verified confirmation and explicit unpaid closure. Real Cashfree sandbox checkout, asynchronous termination, late-payment/refund behavior and the configured merchant's credentials still require validation before enablement.

An uncertain hold can outlast its nominal checkout time. This is a deliberate safety boundary: retain the reservation until the provider resolves it rather than allocate one slot to two paying patients. Operators investigate repeated uncertainty in the original merchant account. Bank settlement confirmation remains separate (ADR 0023).
