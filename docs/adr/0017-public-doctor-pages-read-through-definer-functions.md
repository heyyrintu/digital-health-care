# ADR 0017: Public doctor pages read through definer functions

- **Status:** Accepted
- **Date:** 2026-10-18
- **Deciders:** Tech lead, platform owner
- **Related:** Build Plan §5.1 (`/doctor/[slug]`), §9.1 Priority; ADR 0014 (row-level security); ADR 0016 (platform console functions); threat model T25; API guide §3u

## Context
The public website has a page per doctor at `/doctor/<slug>`: who they are, their verified registration, the clinics they work at, consultation types and fees, and a **Book an appointment** button into the patient portal. It is read by anyone, without a sign-in, and the address is the platform's (one namespace for every organisation), so the API must find a doctor by slug across organisations with no user and no organisation in the request.

ADR 0014 runs every tenant query as `dhc_app` with one organisation set; nothing in a public request says which organisation that is. Looking the slug up first and then switching into that organisation (as the QR check does for prescriptions) would run the rest of the request with full `dhc_app` rights inside the doctor's organisation: a bug in the page's query could then read patients. The owner role bypasses row-level security entirely and must never serve requests.

## Options considered
| Option | For | Against |
|---|---|---|
| Look up the organisation by slug (as `dhc_auth`), then `withTenant` into it | No new database objects; like `/verify` | The anonymous request runs with full tenant read rights in the doctor's organisation: one wrong include reads clinical rows |
| Run the read as the owner role | Simple | Bypasses row-level security for an unauthenticated route; forbidden by ADR 0014 |
| A separate published table or cache (copy on save) | Reads touch no tenant table | A second copy to keep in step with renames, clinic and fee changes, verification and membership changes; stale or leaked if a trigger is missed |
| `SECURITY DEFINER` functions returning only the published columns, called as `dhc_app` with no organisation set | The database fixes what an anonymous request can learn; one place for the "shown" rule; tests pin columns and grants | Each new public field is a migration; definer functions bypass row-level security, so they are reviewed like policies |

## Decision
- **Data:** `doctor_profiles` gains `public_slug` (unique across all organisations; lowercase letters, digits and single hyphens, 3–60), `listed` (default false), `about` (1–1000 characters), `languages` (up to 8 names of 1–40 characters, each once), and `public_updated_at`. CHECK constraints enforce the formats; a listed profile must have a slug. Migration `20261018150000_public_doctor_pages`.
- **Shown** only when all hold: listed; verification `verified`; the doctor's membership in the organisation is an active `doctor` membership; the user is active; the organisation is active. Any other address (missing, malformed, unlisted, unverified, suspended) gets the same `404 NOT_FOUND`, so the API does not say which.
- **Read functions** (owner, `SECURITY DEFINER`, fixed `search_path`, `EXECUTE` revoked from `PUBLIC`, granted only to `dhc_app`):
  - `public_doctor_profile(slug)`: slug, display name, qualifications, specialty, registration number and council (verified, since unverified pages are not returned), about, languages, the organisation's slug and name, the clinics (name and address) and consultation types (name, mode, minutes, fee in paise) the doctor has a schedule for that is in force today (IST) or starts later and has sessions, active ones only, and the time of the last public change.
  - `public_doctor_slugs()`: slug and last public change of every page shown, for a sitemap (at most 50,000).
  - Never a patient, an appointment, an email or mobile, a clinic phone, the signing PIN or any internal ID.
- **Called through `withPublic(db, fn)`** in `@dhc/db`: `SET LOCAL ROLE dhc_app` with the organisation setting empty. In that state row-level security hides every row of every tenant table and `users` is not granted at all, so the functions are the whole surface. The routes `GET /v1/public/doctors/{slug}` and `GET /v1/public/doctors` are public and rate-limited per address (120 per minute). A shown page is sent with `Cache-Control: public, max-age=60, s-maxage=300` (browsers a minute, shared caches five minutes; the cached `x-request-id` is the filling request's, which names no one), a 404 with `no-store`. The API maps the function row to the contract field by field and Zod strips anything else.
- **Editing** stays inside the organisation: `PATCH /v1/doctor-profile/public` runs as `dhc_app` under the doctor's organisation, doctor role only (own profile), and audits `doctor_profile.public_updated` with the changed field names only. A slug taken anywhere is `409 slug: taken`, detected by that unique index alone (`doctor_profiles_public_slug_key`; any other database error is rethrown), which does not say which organisation holds it; a CHECK the contract missed is a 400 on its field. A short list of reserved addresses (`admin`, `api`, `app`, `clinic`, `doctor`, `doctors`, `help`, `login`, `platform`, `robots`, `sitemap`, `support`, `verify`, `www`) is refused by the contract.
- **Web:** `/doctor/[slug]` is rendered on the server and kept for 300 seconds (ISR). It first checks the address against the sitemap list (`GET /v1/public/doctors`, kept in Next's fetch cache for 300 seconds) and answers an address not on it with `notFound()` without calling the single-doctor API, so probing made-up addresses costs the API one list call per five minutes at most; the price is that a newly listed page can take up to five minutes to appear. The visitor's address is not passed on to the API: reading request headers would make the page dynamic and end the caching. A 429 or an API failure shows a "busy, try again" page (the route's error boundary), and nothing is cached for it. `/sitemap.xml` and `/robots.txt` come from the same list. The page has `generateMetadata` (title, description, canonical, OpenGraph; the site address from `PUBLIC_SITE_URL` or `WEB_BASE_URL`, required in production) and schema.org `Physician` JSON-LD whose text is escaped so it cannot close its script tag. **Book an appointment** goes to `/app/login?clinic=<organisation slug>&next=/app/book?doctor=<slug>`; the portal follows `next` only to its own pages and the booking page picks the doctor whose listed slug matches (the booking options now carry `publicSlug` for listed, verified doctors). A link naming a doctor the clinic does not list picks nobody, and the patient chooses; a patient signed in at another clinic than the link's is asked to sign out first rather than taken to the wrong clinic's booking.

## Consequences
- What an anonymous visitor can learn about an organisation is exactly what these functions return, and only for listed, verified doctors. Integration tests (`apps/api/test/public-doctors.int.test.ts`) pin the functions' output columns, that only `dhc_app` may execute them (not `dhc_auth` or `dhc_platform`), that `withPublic` sees no tenant row, that unlisted and unverified pages return nothing, and that no ID, contact, PIN or patient data appears in the answer.
- The functions run as the owner and bypass row-level security. Adding a column or changing the "shown" rule is a security review, as for ADR 0016.
- A doctor who unlists the page, or whose verification or membership ends, disappears from the API at once and from the web within the five-minute cache.
- Each web instance is one address to the API's rate limit, with its own cache. Pages cached for five minutes and the list check keep it well under the limit, but a burst of first visits to many real pages, or someone calling the API directly from many addresses, can still use it up; then the public pages show "busy" for everyone until the minute passes. A CDN or WAF rate limit per client in front of both the public site and the API is still needed, for scraping and for availability (threat model T25).
- Only the doctor edits their own page, as for the prescription pad. A clinic admin editing doctors' pages, per-clinic choice of what is shown, and photos are not provided.

## Review trigger
A public field that is not the doctor's own published text or the organisation's public details; a public search across doctors in the API (the home page's search runs in the browser over the directory, see the addendum), or more than 500 listed doctors; letting staff other than the doctor publish a page; or caching the pages outside our infrastructure.

## Addendum (2026-10-18): the home page directory
The public home page `/` lists the doctors shown, with a client-side search ("Find a doctor"). It reads them through a third function of the same kind, in its own migration `20261018180000_public_doctor_directory`:
- `public_doctor_directory()` (owner, `SECURITY DEFINER`, `search_path` pinned, `EXECUTE` revoked from `PUBLIC`, granted only to `dhc_app`): for every page shown, by the same rule as the other two (listed, verified, an active doctor membership, an active user, an active organisation), only the card's fields: slug, display name, qualifications, specialty, the organisation's name, each scheduled clinic's name and the first line of its address (`addressLine`), the languages and the lowest fee (paise) of the consultation types the doctor is scheduled for. The clinic table holds one free-text address and no city, so the first line is what there is: carriage returns dropped, spaces and tabs trimmed, and a line over 120 characters cut at a word boundary with an ellipsis; none when the line is empty. Clinics and fees come from the same schedules as the page (in force today or later, with sessions, active clinic and type; every join also checks the organisation). Every value is already on the doctor's own page; the directory publishes nothing new, but it lists every shown doctor in one answer (threat model T25: enumeration is intended).
- **At most 500 cards, by name** (a leading "Dr" title ignored: `^dr(\.\s*|\s+)`, so "Dr. Drishti" sorts as "Drishti" and "Dreamcare" keeps its letters; then by address). The page searches the list in the browser, so the list must stay small enough to send whole; beyond 500, doctors late in the alphabet are left out of the home page (their own pages and the sitemap are unaffected). The API logs a warning when the list is full. Reaching a few hundred listed doctors is the trigger to move the search into the API with paging.
- **API:** `GET /v1/public/doctor-directory`, public, with the same limit (120 per minute per address) and `Cache-Control: public, max-age=60, s-maxage=300` as `/v1/public/doctors`; the service maps each row to the contract field by field (`toPublicDoctorCard`).
- **Web:** `/` is rendered per request (like the sitemap). It is not a static (ISR) page because the build has no API (it would ship a "list unavailable" page) and an ISR page would keep that note for five minutes after a failure. The hero and sign-in links stream at once; the directory renders in its own `<Suspense>` boundary and waits at most 3 seconds for the API (`AbortSignal.timeout`). Search and the specialty filter run over the fetched list in the browser; no keystroke reaches the API. Cards are plain links (no prefetch, so scrolling the list renders no doctor pages). `generateMetadata` gives the title, description, canonical and OpenGraph; the JSON-LD is a schema.org `WebSite` (name and address only), escaped like the doctor page's.
- **Caching, per web instance:** the directory and the sitemap list are kept in Next's fetch cache of each web instance (not shared between instances), so the API sees about one call per instance per cache period. After the period the next visitor still gets the kept answer while a fresh one is fetched in the background (stale while refreshing); a doctor page being regenerated waits for the fresh list instead. So a change can take up to one cache period plus one visit to show on the home page. A 429, a failure or a timeout shows "Doctor list unavailable, try again later" only when that instance has no kept list yet; with one, visitors get the kept list and the failed refresh goes unseen. Failures are never kept. A 200 whose body the contract refuses *is* kept (the fetch cache stores the response before it is checked), so a malformed answer shows "unavailable" until it is replaced one period later; the API's own contract check makes that unlikely.
- **Cache seconds:** the period is 300 seconds, or shorter with `PUBLIC_API_CACHE_SECONDS` (60–300). Below 60 is accepted only together with the test-only flag `DHC_E2E=1`, which the browser tests' web server sets with 1; without the flag a lower value is raised to 60 with one warning, so a stray setting cannot multiply calls to the API. The browser tests need it because with five minutes the first test to open a doctor page fixed the list for five minutes, and a doctor another test listed seconds later got a 404. With 1 second a doctor page still always sees a fresh list (regeneration waits for it), but the home page's first visit after a change can still get the previous list, refreshed in the background; the browser test therefore reloads until its doctor shows.

## Addendum 2 (2026-10-19): per-organisation branding
A clinic admin may brand the organisation (Build Plan §5.1 "per-organisation branding", §6.7 "theme, logo and text load at request time"): a display name, an accent colour, a tagline and a logo, shown on its doctors' pages and on the patient portal's sign-in and frame; its cards in the home page directory show the display name only. Custom domains and subdomains are not part of this (infrastructure, later). Migration `20261019090000_organisation_branding`.
- **Its own table, `organisation_branding`**, not more columns on `organisation_settings`. The settings are internal (chart model, safety tuning, upload limits) and every staff role reads them; this row is published to anonymous visitors through definer functions. Separate, a definer function never reads a row that also holds internal settings, a future setting cannot become public by a careless `SELECT *`, and the logo's file metadata sits with the text it brands. One row per organisation; none until an admin saves (no row: the platform look). Row-level security as for every tenant table; CHECKs enforce the formats (name 1–80 and tagline 1–120 characters, trimmed, without control, bidirectional (U+061C, U+200E–U+200F, U+202A–U+202E, U+2066–U+2069) or invisible (U+200B–U+200D, U+2060, U+FEFF) characters; `#rrggbb` lowercase; logo PNG, JPEG or WebP, 1–524288 bytes, a 64-hex SHA-256, all four logo fields or none, and a file key inside `organisations/<own id>/branding/`).
- **Colour contrast is refused, not warned:** the accent is the background of buttons with white labels, so a colour giving white text less than 4.5:1 (WCAG AA) is a 400. A warning would let a clinic publish unreadable Book buttons on every page; refusing keeps the rule in one place (`isReadableAccent` in `@dhc/contracts`) and lets the web apply the colour without a second judgement. The contrast rule is not a CHECK (the database checks the format only), so the API and the database can never disagree on rounding at the boundary. An emptied colour field (`""`) clears the colour, like `null`.
- **Logos** are stored in the private file store like test results, never in the database or at a guessable public path. Uploads are checked byte by byte (threat model T26): the magic numbers decide the type and must match the declared one; SVG is refused; animation is refused (APNG, animated WebP); the whole structure is walked (a JPEG needs exactly one frame header, before its first scan) and must end where the image ends (no appended payloads: polyglots); the first kilobyte and every metadata block, with compressed PNG text inflated, may hold no markup or document header; at most 512 KB, 4096 pixels on a side and 4 million pixels in all.
- **Files and failures:** a replaced or removed logo's file is deleted after the change commits (a logo is not a clinical record). If the upload's transaction fails, the row is read again: if it points at the new file the change did commit (the answer was lost) and the replaced file goes, otherwise the new file goes. One branding change per organisation runs at a time (an advisory lock), so concurrent uploads leave one logo and remove the others' files. **Orphans are possible and accepted for now:** a file whose deletion fails (the store is down), or whose fate is unknown because the row could not be read again, stays in `organisations/<id>/branding/` with no row pointing at it. Each case is logged as an error. Orphans are never served (the logo route finds files only through a row) and hold no patient data; there is no sweeper yet. Removing them is a manual clean-up: any key under `branding/` that no `organisation_branding.logo_key` names can be deleted (backup and restore runbook).
- **Read functions**, as the others (owner, `SECURITY DEFINER`, `search_path` pinned, `EXECUTE` revoked from `PUBLIC`, granted only to `dhc_app`), shown only for an **active** organisation with a saved row:
  - `public_organisation_branding(slug)`: the organisation's slug and name (already public through its doctors' pages and clinic links), display name, accent colour, tagline and the logo's SHA-256.
  - `public_organisation_logo(sha256)`: every active organisation's copy of that logo (file key, media type and size), newest first, at most 8. Organisations may upload the same bytes; the API tries each copy in turn and serves the first that still reads and passes its checks, so one organisation's lost or damaged file never takes another's logo down, and a suspended organisation's copy is never used. The keys name the organisations' folders and go to the API only, which reads files with them and never sends them on; this is the one internal value a public function returns, and only to the server.
  - `public_doctor_directory()`, **version 2**: the previous function with one more column, the card's `organisation_display_name` (a left join on the branding row). The home page stays unbranded, so the colour and logo are not in the list. A function's output columns cannot change with `CREATE OR REPLACE`, so the migration drops and creates it in one transaction; the body is otherwise the previous one, unchanged (same "shown" rule, clinics, fee, order and cap).
  - `public_doctor_profile(slug)` is **not** changed: the API reads the page's header branding with `public_organisation_branding`, by the `organisation_slug` the page already returns, in the same `withPublic` transaction. One function holds the branding rule for the page and the portal, and the long profile function is not copied into a new migration.
- **API:** `GET /v1/public/organisations/{slug}/branding` (public, 120 per minute per address, `public, max-age=60, s-maxage=300`; any slug not shown, malformed ones included, the same 404 `no-store`), and `GET /v1/public/logos/{sha256}` (public, 600 per minute per address because each visitor's browser fetches the logos itself). The logo is addressed by its content hash, so the address names no organisation and changes with the file. Each API instance keeps up to 64 verified logos in memory by hash (bytes and type), so a busy page costs one database lookup per request, not a file read; the lookup still runs every time, so a suspended organisation's or a removed logo stops at the API at once. A logo is sent with the verified `Content-Type`, `nosniff`, `default-src 'none'; img-src 'self'; sandbox`, `Cross-Origin-Resource-Policy: cross-origin` and `public, max-age=300, s-maxage=300`: short, although the address is immutable, so a suspended organisation's logo stops showing within five minutes. Every logo URL the API gives is `public/logos/<sha256>`, relative to the API's base URL. The page's `organisation.branding` is `{displayName, accentColour, logoUrl}` and the card's `organisationDisplayName` a name, all null without branding; the contract defaults them when missing, so a web instance reading an API from before this change still renders. Editing: `GET`/`PUT /v1/organisation-branding`, `POST`/`DELETE /v1/organisation-branding/logo`, clinic admin only, inside the organisation, audited as `organisation.branding_updated` with field names only.
- **Web:** only the validated colour reaches CSS, as variables on the branded element (`--brand-accent`, and `--primary`, `--primary-foreground: #ffffff`, `--ring` inside it), re-checked in the browser with the same rule; missing or failing, the platform theme stays. No CSS, class names or URLs come from data; the logo is an `<img>` only for an address of the known shape, joined to the API's base URL. The doctor page (still ISR, 300 seconds) shows the logo and display name above the profile and uses the accent for its buttons. The portal's sign-in reads the public branding in the browser for `?clinic=` only, and shows it only while the clinic field still holds that clinic (a typed, changed or remembered ID gets the platform look); the portal's frame reads it for the signed-in organisation, without the patient's token, and uses the accent only for the clinic's own marks (a stripe and the initial's tile), not for tabs drawn on tinted backgrounds. The home page `/` stays unbranded: a card's "At …" line uses the display name, with no logo or colour.
- **Consequences:** branding is now part of what an anonymous visitor can learn about an organisation, but only what its admin chose to publish; the integration tests (`apps/api/test/branding.int.test.ts`, and the column and grant pins in `public-doctors.int.test.ts`) pin the columns, grants, the active-only rule, the logo checks, the copies fallback, failures and tenancy. A change of branding shows on the doctor pages, the sign-in and the logo within five minutes (the caches of the page, the API answers and the logo).
- **Review trigger:** branding fields beyond these (a favicon, fonts, a second colour, dark mode), any CSS or HTML from data, SVG or animated logos, logos served from another origin or a CDN, custom domains, branding the Patient app, PDFs or messages, or orphaned logo files growing enough to need a sweeper.
