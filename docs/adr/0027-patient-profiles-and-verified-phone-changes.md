# ADR 0027 — Patient web profiles and verified phone changes

Date: 2026-11-05. Status: accepted for local implementation.

## Profile and clinical boundaries

An authenticated patient can view/edit each currently owned live family profile in the current clinic. Current onboarding consents and verified-number/guardian ownership are checked inside tenant transactions. Merged duplicates are read-only; use the kept profile. Demographic writes lock the patient row and require the displayed `updatedAt`, preventing a stale form from overwriting staff edits. Allow only name, DOB, gender, language, email, address, paired emergency contact details and a separately reported blood group. The API normalizes Indian mobile numbers and rejects invalid dates and changes that would turn an unguarded adult or existing guardian into a child. UHID, guardian links, verified phone and clinic-recorded blood group cannot be overridden through this form. Email is contact information, not a verified sign-in identity.

Patient medical reports always use `source=patient`; the client cannot choose a trusted source or remove doctor facts. The existing safety engine continues to label/evaluate these facts as unverified (SR-21). Doctors confirm through chart-permission checks: a confirmation creates a doctor entry and retires the original patient entry, preserving its provenance and history. Signed prescriptions and their recorded safety outcomes are unchanged. Reported blood group stays separate from the clinic-recorded value until a doctor confirms the exact profile version. Existing clinic-recorded blood groups are not retrospectively represented as doctor-verified. Corrections/removals of existing clinical entries remain clinic-controlled.

Photos are private, authenticated, no-store resources, not public avatar URLs. Reuse the bounded still-image validation (JPEG/PNG/WebP, 512 KB, maximum 4096 pixels per side and four million pixels), rejecting markup, animation, malformed content and mismatched media. The file store uses new unpredictable keys. Ownership is checked before storage work and again under the row lock. Replaced/removed non-clinical photos are deleted after commit; failed uploads recheck the committed pointer before cleanup. Storage uncertainty retains a possible orphan rather than breaking a committed photo; failures are logged for cleanup, as with branding. The browser keeps only a revocable blob URL, removed on unmount/sign-out. Production S3/scanning and durable orphan cleanup remain part of the wider storage backlog.

## Phone-change scope and proof

A self-service transfer moves one selected adult's live profile and access to dependants without their own phone in one clinic. Other adults sharing the old number, other clinics, global user phone identities and staff sessions are unchanged. Both numbers must be controlled now. A lost old number, a child/guarded profile, a suspended/revoked account or existing clinic records on the proposed new number requires clinic assistance; there is no self-service bypass or automatic clinical-record merge.

Issue dedicated `phone_change` OTP challenges through the existing WhatsApp authentication transport. A phone-change code is never accepted by the sign-in verifier. Challenges are bound server-side to one request UUID, actor, clinic, patient and normalized old/new numbers. Five-minute expiry, five wrong attempts per challenge, shared per-phone issuance limits and three change requests per account per hour apply. Failed verification counters commit even though the request fails. Audit entries record IDs/actions, never codes or phone values.

Claim the request UUID durably before external delivery. A retry returns the existing preparation state and never sends another pair automatically. If delivery/process failure leaves preparation incomplete, the user may explicitly start another request within the limits. No unbound or partially prepared proof can transfer a profile. Meta's configured approved authentication template must be accepted for this verification use before live activation; no new provider was added.

Verification locks the request/challenges and serializes creation of the new phone's identity with sign-in, clinic registration and portal family creation. Recheck current consents, live ownership, adult status, source/target access and clinic collisions. One transaction switches between the restricted auth and tenant roles: identity work stays under `dhc_auth`; clinical/profile queries stay under the current `dhc_app` tenant. Never run patient queries as an unrestricted owner. The new proof table is an auth-only identity table; neither tenant nor platform roles can read it.

On success, retain patient/guardian IDs, UHIDs and all history, bind the selected clinic profile to the verified destination identity, consume both proofs and revoke affected patient sessions/push registrations in this clinic. Do not transfer consents or WhatsApp preferences to a different number. Source-number opt-ins remain attached to that number; existing send-time recipient/consent checks suppress stale notices. The destination signs in normally and accepts required consents. After an uncertain response, signing in on the new number and checking the family is the recovery path. There is no token-bearing result stored or returned by the transfer endpoint.

## Scope limits

The lost-number path is in-person clinic identity verification followed by the clinic's existing controlled demographic process; this increment does not add remote identity proofing or automatically merge existing accounts/records. Global multi-clinic identity migration, phone changes for native clients, production cloud DSC and AI remain outside this increment. Native development remains paused. No PR/deployment or real provider messages were performed.

## Validation

API coverage checks ownership/tenant/consent/merge boundaries, strict protected-field rejection, version conflicts, paired emergency contacts, guardian-age rules, photo validation/private reads/removal, doctor-only/chart-restricted confirmation, original clinical history, exact blood-report version, purpose isolation, persisted wrong-code limits, expiry, current-clinic collision, single-request issuance during concurrent retries, concurrent completion, revoked access and preservation of other adults/clinics. Browser coverage edits the profile, reports an unverified allergy, uploads/removes a photo, verifies both numbers, signs in anew and finds the dependant on 390px and 1280px layouts. Clinic browser coverage confirms blood group and a patient-reported allergy without deleting its original history. Local synthetic verification does not replace real Meta or clinical/staging acceptance.

Validation: all 43 migrations applied to fresh disposable databases; 128 affected API integration tests across eight suites passed; 52 scoped web/API/worker/shared checks passed; all 69 web browser tests passed, including clinic-side blood/allergy confirmation. After the final immediate-name refresh fix, 15 web/browser check tasks and both 390px/1280px profile/phone-change browser scenarios passed again. Formatting and diff checks passed. Real Meta delivery, production storage/scanning and staging acceptance remain separate.
