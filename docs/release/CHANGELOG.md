# Changelog

All notable changes are recorded here, newest first. Format: version, date, summary, link to release notes.

## [Unreleased]
- Project set-up: monorepo, CI, environments (phase 0).
  - pnpm + Turborepo monorepo with apps (api, workers, web, mobile) and shared packages (contracts, api-client, domain, safety, i18n, tokens, config).
  - API skeleton: `/v1/health`, `/v1/openapi.json`, standard error shape, request IDs.
  - Workers on BullMQ; web route areas with security headers; Expo Patient/Clinic variants with EAS profiles.
  - CI: format, lint, typecheck, test and build on every pull request.
- Auth and tenancy (phase 0 exit criterion).
  - `packages/db`: Prisma schema and migrations for organisations, users, memberships, sessions, OTP challenges, patients and an append-only audit log; Postgres row-level security with `dhc_app` / `dhc_auth` roles (ADR 0014).
  - Patient sign-in by mobile code; staff sign-in by password + authenticator (TOTP) with first-login enrolment and lockout; rotating refresh tokens with reuse detection; logout takes effect immediately.
  - Staff patient search and view (each view audited); clinic-admin audit log.
  - Integration suite for auth and tenant isolation, run against Postgres in CI.
  - Development seed with synthetic personas.
- Staff invite links: clinic admins invite staff by email or mobile; the single-use link (72 h) is the only way to set a staff password and enrol an authenticator. Login no longer offers enrolment. Existing staff accounts confirm with their current password and authenticator. Seed now prints invite links.
- Web `/invite` page: checks the link, sets (or confirms) the password, shows the authenticator QR code and typed key, and confirms the first code; English and Hindi. The API now allows the web app's origin via CORS.
- Staff web sign-in: `/clinic/login` (password, authenticator code, role choice) and a signed-in `/clinic` dashboard with patient search and sign-out. The refresh token stays in an httpOnly cookie behind the web app's `/api/session` routes; the page keeps only the 15-minute access token. Reloads keep the session; 15 minutes idle signs out. Completing an invite now signs the person straight in (ADR 0015).
- Authenticator reset: clinic admins see their staff on the dashboard and can reset someone's sign-in. Reset clears the password and authenticator, ends all their staff sessions and issues a single-use reset link; the person sets new ones on `/invite` and keeps their role. No self-reset; staff who also work at another clinic need platform support (threat model T22).
- Dashboard invite form: clinic admins invite staff by email or mobile with a name and role, get the link to share (with copy), and see pending invites with Revoke. The staff list now shows active staff only.
- Browser tests in CI: a Playwright suite (`apps/e2e`, 11 tests) runs on every pull request against the built API and web app with its own Postgres, uploading screenshots and traces on failure. The web app now reads the API address at render time (`API_BASE_URL`), so one build works in every environment; the API's sign-in rate limit is configurable (`SIGN_IN_RATE_LIMIT`).
- Platform-support reset: a support command (`support-reset-authenticator`, shipped in the API build) resets staff who work at more than one clinic, which clinic admins may not do. It shows the plan and asks for confirmation, signs the person out at every clinic, revokes their open links, issues a reset link for the chosen clinic, and records the ticket, operator and reason in each clinic's audit log. Runbook: identity callback, clinic-admin confirmation, second-person approval.
- Build plan: message links need an OTP or signed-in session before showing prescription or consent content (date-of-birth check only for other pages; threat model T23); D12 and ADR 0012 state the phase count as Phase 0 plus six delivery phases; the next-steps brief names PRD v3.0 (Final). The Word and PDF editions of Oct 6 predate these changes.
- Patient register (phase 1, first slice): front desk, doctors and clinic admins register patients with an automatic UHID (clinic prefix + next number, e.g. EK10001; numbers in use are skipped), see likely duplicates (same mobile and name, or same name and date of birth) before registering again, and edit demographics. Families share a mobile; patients without one link to a guardian. Clinic admins configure UHID numbering and tags (six PRD defaults, colours, sort-to-top, archive); front desk and doctors tag patients, and the patient list filters by tag. Web: register form, patient page (details, tags, family) and clinic settings; English and Hindi. Every view and change is audited without patient data in the log.
- Availability and slot engine (phase 1): clinic admins add clinics, consultation types (mode, minutes per slot, fee and follow-up fee in paise, pay at booking) and booking rules (horizon, same-day cutoff). Doctors set their weekly schedule per clinic and consultation type as versions that apply from a date, so earlier days never change; they add leave (whole or part days) and extra sessions, and admins add clinic holidays; anything not yet started can be withdrawn. A pure slot engine in `@dhc/domain` turns these into one day's slots in IST, with buffers, and applies the horizon and cutoff for patients. Web: **Availability** page (schedule editor, leave and extra sessions, slot preview) and a clinics-and-consultations card for admins; English and Hindi. New tables have row-level security; changes are audited. The seed adds a clinic, two consultation types and Dr. Demo's weekly schedule.
- Appointments (phase 1): front desk, doctors and clinic admins book patients into the doctor's free slots (from the patient page or the appointments list), add walk-ins straight into today's list checked in, overbook a taken slot within the clinic's daily limit, reschedule (the old booking is linked to the new one) and cancel with a reason. Each doctor's patients get a token per clinic per day. Statuses follow PRD §5.2 with every change kept in a history: front desk and doctors check patients in and mark no-shows; the patient's own doctor starts and completes the consultation, and the times are recorded. Booked slots now show as taken in the slot preview. Bookings for a doctor's day are serialised in the database so two people can never take the same slot, and two simultaneous changes to one appointment cannot both succeed. Web: **Appointments** day list with actions, booking page with slot picker, patient-page appointments; English and Hindi. New tables have row-level security; changes are audited without patient details.
- Live queue and waiting-room screen (phase 1): **Queue** replaces the appointments list with tabs My OPD (patient with the doctor first, then checked-in patients with Emergency/Priority first and then by arrival, each with a live waiting time), Booked (with "Awaiting response" for unconfirmed), Completed (with the day's average consultation time) and Cancelled and no-shows; date, doctor, search, tag and mode filters; refreshes every 15 seconds. Doctors see their own queue by default. Clinic admins create waiting-room screen links (shown once, stored hashed, revocable); the kiosk page shows each doctor's current and next tokens in English and Hindi, never names, and keeps itself up to date.
- Consultation screen (phase 1, first consultation slice): doctors open **Consultation** from the queue once the patient has checked in. The left panel shows the patient chart — allergies (highlighted), conditions and current medicines, each added or removed with a reason (removed entries are kept), patient-reported entries labelled unverified — and recent visits with their diagnoses. The right side holds the visit's vitals (BP, pulse, temperature, SpO₂, weight, height, BMI, pain score, pregnancy where relevant; a reminder that children under 12 need today's weight) and the notes: chief complaint, symptoms with duration, examination, diagnoses from an ICD-10 starter list or free text, plan, tests advised, advice, private notes and a follow-up date with one-tap booking. Notes save automatically, are encrypted at rest, and a second tab cannot overwrite newer notes. Front desk records vitals from the queue (**Vitals**) but cannot see notes or the chart; clinic admins have no clinical access. Every view and change is audited. English and Hindi.
- Prescription builder (phase 1, second consultation slice): on the consultation screen doctors search the medicine master by name or composition (a synthetic sample of generic products in development; the licensed database later) or add a free-text medicine, which is marked as not in the list. Each line takes dose, frequency (1-0-1 patterns, OD/BD/TDS/QID/HS/SOS/STAT, weekly, monthly, alternate days or free text), duration, timing, route, quantity and instructions; tapering courses have several steps. The printed remark is written automatically in English or Hindi (the patient's language by default) and can be edited. **Repeat last** adds the patient's previous prescription; doctors save and apply their own templates. Lines autosave with the same stale-tab protection as the notes. The clinic tables have row-level security: clinics read the shared reference master but cannot change it, and their own medicines are private; the reference molecule list is read-only to clinics. Every view and change is audited. Database triggers keep each prescription on its own appointment (same clinic, patient and doctor) and each line on a prescription of the same clinic.
- Design system theme (step 1 of `ui-web`): `@dhc/tokens` now carries the theme from the approved demo (the Lovable prototype): semantic colours in light and dark (shadcn names such as `primary`, `muted-foreground`, `success-soft`, plus `ai` and `wa`), Figtree for text and Manrope for headings with Noto Sans Devanagari for Hindi, a 16 px base radius, shadows and gradients. Light destructive, success and info are slightly darker than the demo and dark mode uses dark text on them, so every text pairing meets WCAG AA (4.5:1); a test checks this. Mobile gets the same colours as hex (`themeHex`). The web app runs Tailwind v4 on this theme (`bg-primary`, `rounded-xl`, `font-display`, `shadow-soft`; dark mode via a `dark` class on `<html>`, no switch yet). The existing screens' CSS sits in a `legacy` cascade layer below Tailwind's utilities and Tailwind's reset is held back, so those screens look exactly as before until they move to the design system.
- Design system components (step 2 of `ui-web`): new package `@dhc/ui-web` with the demo's shadcn/ui primitives (button, input, textarea, label, select, checkbox, radio group, switch, one-time code, calendar, dialog, alert dialog, drawer, sheet, popover, dropdown menu, command, tooltip, tabs, table, badge, card, skeleton, separator, scroll area, toasts) and clinic components reworked from the demo: page header, surface, stat, empty state, field, status chip and mode tag (names from `@dhc/i18n`), tag chip (colour as border and dot, as before), avatar, status timeline, action sheet and tiles, date strip and slot picker (the API's slots grouped into morning, afternoon and evening; staff can pick a taken slot when overbooking), and the staff shell (collapsible sidebar, phone top bar and bottom tabs, Ctrl/⌘-K page search). Components take data as props and never fetch; their own text (close buttons, section names, screen-reader labels) follows `UiLocaleProvider`, in English and Hindi, and calendar day and month names follow it too. The demo's mock store, fake sign-in, demo idle timer and theme switch were left out. The web app builds with the package and its styles; no screen uses it yet, so screens look as before.
- Web screens on the design system (step 3 of `ui-web`): every web screen now uses the theme and `@dhc/ui-web`, and the hand-written `globals.css` is gone (Tailwind's reset is on). Staff pages sit in the demo's frame: a sidebar with the pages each role may use (dashboard, queue, availability, register patient), the language switch, a role badge, a "Jump to a page" search (Ctrl/⌘-K) and sign-out; on phones a top bar and a scrolling page list. Queue, Availability and Register patient moved from dashboard buttons into that navigation. The sign-in and invite pages are centred cards; the dashboard, patient register, availability, booking, queue (segmented tabs, token tiles), vitals and consultation screens (chart beside vitals, notes and the prescription builder on large screens) use cards, page headers and status chips; the waiting-room display is dark with large tokens for TVs. Text, behaviour, labels and roles are unchanged.
