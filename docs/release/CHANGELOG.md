# Changelog

All notable changes are recorded here, newest first. Format: version, date, summary, link to release notes.

## [Unreleased]
- Project set-up: monorepo, CI, environments (phase 0).
  - pnpm + Turborepo monorepo with apps (api, workers, web, mobile) and shared packages (contracts, api-client, domain, safety, i18n, tokens, config).
  - API skeleton: `/v1/health`, `/v1/openapi.json`, standard error shape, request IDs.
  - Workers on BullMQ; web route areas with security headers; Expo Patient/Clinic variants with EAS profiles.
  - CI: format, lint, typecheck, test and build on every pull request.
- Auth and tenancy (phase 0 exit criterion).
  - `packages/db`: Prisma schema and migrations for organisations, users, memberships, sessions, OTP challenges, patients and an append-only audit log; Postgres row-level security with `dhc_app` / `dhc_auth` roles (ADR 0014).
  - Patient sign-in by mobile code; staff sign-in by password + authenticator (TOTP) with first-login enrolment and lockout; rotating refresh tokens with reuse detection; logout takes effect immediately.
  - Staff patient search and view (each view audited); clinic-admin audit log.
  - Integration suite for auth and tenant isolation, run against Postgres in CI.
  - Development seed with synthetic personas.
- Staff invite links: clinic admins invite staff by email or mobile; the single-use link (72 h) is the only way to set a staff password and enrol an authenticator. Login no longer offers enrolment. Existing staff accounts confirm with their current password and authenticator. Seed now prints invite links.
- Web `/invite` page: checks the link, sets (or confirms) the password, shows the authenticator QR code and typed key, and confirms the first code; English and Hindi. The API now allows the web app's origin via CORS.
- Staff web sign-in: `/clinic/login` (password, authenticator code, role choice) and a signed-in `/clinic` dashboard with patient search and sign-out. The refresh token stays in an httpOnly cookie behind the web app's `/api/session` routes; the page keeps only the 15-minute access token. Reloads keep the session; 15 minutes idle signs out. Completing an invite now signs the person straight in (ADR 0015).
- Authenticator reset: clinic admins see their staff on the dashboard and can reset someone's sign-in. Reset clears the password and authenticator, ends all their staff sessions and issues a single-use reset link; the person sets new ones on `/invite` and keeps their role. No self-reset; staff who also work at another clinic need platform support (threat model T22).
- Dashboard invite form: clinic admins invite staff by email or mobile with a name and role, get the link to share (with copy), and see pending invites with Revoke. The staff list now shows active staff only.
- Browser tests in CI: a Playwright suite (`apps/e2e`, 11 tests) runs on every pull request against the built API and web app with its own Postgres, uploading screenshots and traces on failure. The web app now reads the API address at render time (`API_BASE_URL`), so one build works in every environment; the API's sign-in rate limit is configurable (`SIGN_IN_RATE_LIMIT`).
- Platform-support reset: a support command (`support-reset-authenticator`, shipped in the API build) resets staff who work at more than one clinic, which clinic admins may not do. It shows the plan and asks for confirmation, signs the person out at every clinic, revokes their open links, issues a reset link for the chosen clinic, and records the ticket, operator and reason in each clinic's audit log. Runbook: identity callback, clinic-admin confirmation, second-person approval.
- Build plan: message links need an OTP or signed-in session before showing prescription or consent content (date-of-birth check only for other pages; threat model T23); D12 and ADR 0012 state the phase count as Phase 0 plus six delivery phases; the next-steps brief names PRD v3.0 (Final). The Word and PDF editions of Oct 6 predate these changes.
- Patient register (phase 1, first slice): front desk, doctors and clinic admins register patients with an automatic UHID (clinic prefix + next number, e.g. EK10001; numbers in use are skipped), see likely duplicates (same mobile and name, or same name and date of birth) before registering again, and edit demographics. Families share a mobile; patients without one link to a guardian. Clinic admins configure UHID numbering and tags (six PRD defaults, colours, sort-to-top, archive); front desk and doctors tag patients, and the patient list filters by tag. Web: register form, patient page (details, tags, family) and clinic settings; English and Hindi. Every view and change is audited without patient data in the log.
- Availability and slot engine (phase 1): clinic admins add clinics, consultation types (mode, minutes per slot, fee and follow-up fee in paise, pay at booking) and booking rules (horizon, same-day cutoff). Doctors set their weekly schedule per clinic and consultation type as versions that apply from a date, so earlier days never change; they add leave (whole or part days) and extra sessions, and admins add clinic holidays; anything not yet started can be withdrawn. A pure slot engine in `@dhc/domain` turns these into one day's slots in IST, with buffers, and applies the horizon and cutoff for patients. Web: **Availability** page (schedule editor, leave and extra sessions, slot preview) and a clinics-and-consultations card for admins; English and Hindi. New tables have row-level security; changes are audited. The seed adds a clinic, two consultation types and Dr. Demo's weekly schedule.
- Appointments (phase 1): front desk, doctors and clinic admins book patients into the doctor's free slots (from the patient page or the appointments list), add walk-ins straight into today's list checked in, overbook a taken slot within the clinic's daily limit, reschedule (the old booking is linked to the new one) and cancel with a reason. Each doctor's patients get a token per clinic per day. Statuses follow PRD §5.2 with every change kept in a history: front desk and doctors check patients in and mark no-shows; the patient's own doctor starts and completes the consultation, and the times are recorded. Booked slots now show as taken in the slot preview. Bookings for a doctor's day are serialised in the database so two people can never take the same slot, and two simultaneous changes to one appointment cannot both succeed. Web: **Appointments** day list with actions, booking page with slot picker, patient-page appointments; English and Hindi. New tables have row-level security; changes are audited without patient details.
- Live queue and waiting-room screen (phase 1): **Queue** replaces the appointments list with tabs My OPD (patient with the doctor first, then checked-in patients with Emergency/Priority first and then by arrival, each with a live waiting time), Booked (with "Awaiting response" for unconfirmed), Completed (with the day's average consultation time) and Cancelled and no-shows; date, doctor, search, tag and mode filters; refreshes every 15 seconds. Doctors see their own queue by default. Clinic admins create waiting-room screen links (shown once, stored hashed, revocable); the kiosk page shows each doctor's current and next tokens in English and Hindi, never names, and keeps itself up to date.
- Consultation screen (phase 1, first consultation slice): doctors open **Consultation** from the queue once the patient has checked in. The left panel shows the patient chart — allergies (highlighted), conditions and current medicines, each added or removed with a reason (removed entries are kept), patient-reported entries labelled unverified — and recent visits with their diagnoses. The right side holds the visit's vitals (BP, pulse, temperature, SpO₂, weight, height, BMI, pain score, pregnancy where relevant; a reminder that children under 12 need today's weight) and the notes: chief complaint, symptoms with duration, examination, diagnoses from an ICD-10 starter list or free text, plan, tests advised, advice, private notes and a follow-up date with one-tap booking. Notes save automatically, are encrypted at rest, and a second tab cannot overwrite newer notes. Front desk records vitals from the queue (**Vitals**) but cannot see notes or the chart; clinic admins have no clinical access. Every view and change is audited. English and Hindi.
- Prescription builder (phase 1, second consultation slice): on the consultation screen doctors search the medicine master by name or composition (a synthetic sample of generic products in development; the licensed database later) or add a free-text medicine, which is marked as not in the list. Each line takes dose, frequency (1-0-1 patterns, OD/BD/TDS/QID/HS/SOS/STAT, weekly, monthly, alternate days or free text), duration, timing, route, quantity and instructions; tapering courses have several steps. The printed remark is written automatically in English or Hindi (the patient's language by default) and can be edited. **Repeat last** adds the patient's previous prescription; doctors save and apply their own templates. Lines autosave with the same stale-tab protection as the notes. The clinic tables have row-level security: clinics read the shared reference master but cannot change it, and their own medicines are private; the reference molecule list is read-only to clinics. Every view and change is audited. Database triggers keep each prescription on its own appointment (same clinic, patient and doctor) and each line on a prescription of the same clinic.
- Safety engine (phase 1, third consultation slice): every save and every opening of a draft checks the lines against the patient's chart and the reference drug data, with rules SR-01 to SR-22. The rules cover allergies (same molecule, same class, cross-sensitivity), interactions, duplicate molecules and classes, drug–condition warnings, pregnancy and breastfeeding, children's weight and mg/kg doses, maximum daily dose across lines, older adults, kidney and liver care, telemedicine lists, missing dose, frequency or duration, and free-text medicines. Alerts show on each line in English or Hindi. Doctors acknowledge warnings and override the blocks the drug data allows, with a reason where the rule needs one. Every alert and answer is kept in a safety log (`safety_alerts`) with the drug data version, and is audited. New reference tables hold molecule facts, interactions, cross-sensitivities and drug–condition rules. Medicines now list ingredients with strengths. The synthetic sample is extended for development and tests; it is illustrative only and needs clinical sign-off before any rule goes live.
- Signing, PDF and QR verification (phase 1, fourth consultation slice): doctors fill in their **prescription pad** (registration number, council, qualifications, specialty, number prefix, A5 or A4) and set a 6-digit signing PIN confirmed with their password; the platform team verifies the registration with a new support command (`support-verify-doctor`), and only verified doctors can sign. On the prescription card, **Preview PDF** shows the draft marked PREVIEW, and **Sign prescription** with the PIN has the server check the safety alerts again, give the next number (e.g. SG-00042), render the PDF (English or Hindi, black and white, with the generic names in capitals and a QR), sign its SHA-256 and store it by key; the lines and the visit record lock. **Amend** starts the next version with a reason (the number stays; the old version becomes superseded when the new one is signed) and **Void** with a reason and the PIN stamps a copy VOID while keeping the signed file. A public page, `/verify/<code>`, shows a pharmacist Genuine, Superseded or Void with the doctor, clinic, the patient's initials and the medicines, in English or Hindi. Signatures use a test key, clearly marked not legally valid, until the cloud Class 3 DSC provider is connected (ADR 0008); production refuses the test key. Database triggers keep signed prescriptions, their lines and safety log unchangeable. Five wrong PINs pause signing for 15 minutes. Every step is audited. Delivery to the patient and amendment notices come with messaging.
- Design system theme (step 1 of `ui-web`): `@dhc/tokens` now carries the theme from the approved demo (the Lovable prototype): semantic colours in light and dark (shadcn names such as `primary`, `muted-foreground`, `success-soft`, plus `ai` and `wa`), Figtree for text and Manrope for headings with Noto Sans Devanagari for Hindi, a 16 px base radius, shadows and gradients. Light destructive, success and info are slightly darker than the demo and dark mode uses dark text on them, so every text pairing meets WCAG AA (4.5:1); a test checks this. The same colours are exported as hex for mobile (`themeHex`); the mobile app moves to them with its screens. The web app runs Tailwind v4 on this theme (`bg-primary`, `rounded-xl`, `font-display`, `shadow-soft`; dark mode via a `dark` class on `<html>`, no switch yet). The existing screens' CSS sits in a `legacy` cascade layer below Tailwind's utilities and Tailwind's reset is held back, so those screens look exactly as before until they move to the design system.
- Design system components (step 2 of `ui-web`): new package `@dhc/ui-web` with the demo's shadcn/ui primitives (button, input, textarea, label, select, checkbox, radio group, switch, one-time code, calendar, dialog, alert dialog, drawer, sheet, popover, dropdown menu, command, tooltip, tabs, table, badge, card, skeleton, separator, scroll area, toasts) and clinic components reworked from the demo: page header, surface, stat, empty state, field, status chip and mode tag (names from `@dhc/i18n`), tag chip (colour as border and dot, as before), avatar, status timeline, action sheet and tiles, date strip and slot picker (the API's slots grouped into morning, afternoon and evening; staff can pick a taken slot when overbooking), and the staff shell (collapsible sidebar, phone top bar and bottom tabs, Ctrl/⌘-K page search). Staff pages sit in the demo's frame: a sidebar with the pages each role may use (dashboard, queue, availability, register patient), the language switch, a role badge, a "Jump to a page" search (Ctrl/⌘-K) and sign-out; on phones a top bar and a scrolling page list. Workflows, data, labels, roles and test ids are unchanged; the deliberate visible changes are the new staff frame and page jump, queue rows showing the consultation mode, and a red (destructive) cancel confirmation.
- Billing and counter payments (phase 1; step 4 of `ui-web`, built on it from the start): clinic admins keep a **Price list** (items billed besides the consultation; repricing affects new bills only, items are deactivated rather than deleted). Front desk and doctors open **Bill** from the queue once the patient has arrived: the consultation or follow-up fee (or none), price-list items with quantities and a discount with its reason. The server prices every line from the clinic's fees and price list and keeps the bill's figures consistent (the database also checks that total = subtotal − discount, that line amounts match their quantity and that a bill's status matches what was paid). **Record payment** takes cash, UPI or card, part or whole, with an optional reference; each payment gets the clinic's next receipt number (R00001…), a retried request records it once, and a bill with a payment can no longer change. Receipts print on A5 without the menus. **Collections** shows a day's payments by mode and by doctor and the visits still due; queue cards show each bill's total and whether it is due, partly paid or paid. Tables have row-level security; triggers keep bills, lines and payments on the same clinic's visit; payments are append-only; every change and receipt view is audited without patient names. Payment links, online checkout, refunds and reconciliation come with Cashfree (phase 3). English and Hindi.
- Same-clinic references everywhere (defence in depth): foreign keys do not see row-level security, so a write scoped to one clinic could still name another clinic's row by ID. A database trigger (one shared function, `same_tenant_reference`) now rejects that for every reference between clinic tables: patient guardians and tags; availability versions and exceptions (clinic, consultation type); appointments (patient, clinic, consultation type, rescheduled-from) and their status history, which the queue reads; waiting-room screens; allergies, conditions and current medicines; vitals and consultations (appointment and patient); and prescription lines' medicines (a platform medicine or the clinic's own). The check compares organisations directly, so it holds for the owner role too, and like the prescription triggers it uses a fixed search_path and raises check_violation (23514). A referenced row (patient, tag, clinic, consultation type, appointment, clinic medicine) also keeps its organisation while anything still points at it, so moving it cannot strand its children in the old clinic; the reference check locks the row it validates, so a concurrent move and a new reference cannot both commit. The services already read each parent under row-level security first; no behaviour changes for valid requests.
- Clinic admin dashboard and audit log (phase 1, PRD §9.2): the dashboard opens with **Clinic at a glance**: appointments, completed visits, cancellations, no-shows and their rate, new patients, prescriptions signed and money collected for today, the last 7 or the last 30 days, with a row per day (`GET /dashboard`, counted in the database under row-level security). A new **Audit log** page (clinic admins, in the menu) lists who did what and when, filtered by area, staff member and IST dates, with **Load more**; `GET /audit-log` gains those filters and the staff member's name, which is never given for patients. Leftover class names from the old stylesheet and stale comments about it are removed. English and Hindi.

Each can be added as a new clinic medicine (prefilled), linked to a listed medicine (doctors searching the typed name then find it), or rejected with a reason; decisions can be undone and existing prescriptions never change. **Medicine list** searches the reference list (read-only) and the clinic's own medicines, which admins add, edit and deactivate with their molecules and strengths so the safety checks can see them. Doctors' free-text option now says the clinic admin will review it. New `medicine_requests` table with row-level security, checks and a same-clinic trigger; every change is audited. English and Hindi.
- Clinic settings (phase 1, PRD §9.2): the dashboard's new **Chart, safety alerts and files** card lets clinic admins choose who sees the chart (**Shared chart**, or **Own patients only**: a doctor sees a patient's chart, notes and prescriptions once the patient is checked in to them), hide the three non-critical safety alerts the catalogue allows (moderate and minor interactions, duplicate class, older-adult caution; blocks and critical alerts cannot be hidden) and set upload limits (largest file up to 25 MB and the accepted types, for the upload features to come). New `organisation_settings` table with row-level security and database checks; changes are audited as `settings.updated`, with a *Settings* area in the audit log. English and Hindi.

- Patient merges (phase 1, PRD §3.2): front desk, doctors and clinic admins ask to merge a duplicate patient record from either record's page (**Merge a duplicate record**: find the other record, choose which stays, give a reason). Clinic admins compare the two side by side under **Patient merges** and approve or reject (with a reason). Approving moves the duplicate's chart entries, tags, upcoming bookings, dependants and patient-app account to the kept record; past visits, prescriptions and bills stay as signed and show under the kept record (chart, visit list, Repeat last, safety follow-up check). The duplicate becomes read-only with a link to the kept record, drops out of search except by its old UHID, and database triggers refuse anything new pointing at it. Merges cannot be undone and are audited. New `patient_merge_requests` table and `patients.merged_into_id`; new error code `PATIENT_MERGED`. English and Hindi.
- Mobile foundation (phase 2): a shared `@dhc/ui-native` package draws the web theme in React Native (light and dark follow the device; text, buttons, fields, 6-digit code field, cards and notices with WCAG AA contrast checked in tests). Signed-out people only reach the sign-in screens. English and Hindi follow the device language, with a switch on the sign-in screen. `@dhc/api-client` gains the sign-in, refresh and `/me` calls.
- Patient accounts (phase 2, first slice of the Patient app API): `/portal` endpoints for signed-in patients. One phone number is one account: its patients are the clinic's records on the verified number and the dependants they look after, so a record registered at the desk is claimed by signing in. Patients accept the privacy notice, terms and a separate health-data consent (versioned; every acceptance kept, health data can be withdrawn), and health data stays closed until all three are in force. Patients add themselves or a family member (adults sharing the number, or children looked after by one of them), each with a UHID. Another account's or another clinic's records are never visible. Audited; a Patient consents area in the audit log.

The API runs the check every `NO_SHOW_SWEEP_SECONDS` (default 60), safely on several instances at once, and calls a live-queue hook that server-sent events will use.

New `push_devices` table (sign-in role only, trigger keeps each device on its own session's person and clinic) and `medicines.updated_at`.

- Fixed: staff sign-in could fail with a 500 under load. The password check (scrypt, slow by design) ran inside a database transaction and could outlast its 5-second limit; it now runs between two short transactions, which also no longer hold a database connection during the check. Failed passwords and codes are now counted atomically, so wrong guesses sent at the same time can no longer stay under the 5-attempt lockout. This was the cause of the intermittent CI failure in the appointments integration tests.
- Fixed: the same 500 under load when accepting a staff invite (password check or new password) and when checking the signing PIN to sign or void a prescription: scrypt now runs between two short transactions, and the second re-reads the invite, account or doctor profile, so an invite revoked or used meanwhile, a lockout, or a password or PIN changed meanwhile is refused (a changed one counts as a wrong attempt). If a new account finishes enrolling through another link meanwhile, accepting answers 409 and asks the person to open their link again instead of replacing that account's password.
- Mobile bundles in CI (phase 2): every pull request bundles the Patient and Clinic apps' JavaScript for iOS and Android (`pnpm --filter @dhc/mobile bundle`, `expo export`), as an EAS build would before compiling, so a missing native module or bundler error shows up without store credentials or a device.
- Claude Code mod `dhc-steward` (`tools/claude/dhc-steward`, tooling only): a build-plan pane (`/dhc`), the CI checks on demand (`/dhc-check`), an orchestrated next increment with builder and reviewer agents (`/dhc-next`), and guards against editing applied migrations, pushing to `main` and force pushes. The repository is a plugin marketplace: `/plugin install dhc-steward --marketplace heyyrintu/digital-health-care`.
- Platform console API (phase 3, PRD §3.2, §9.1, §9.3; ADR 0016; web screens are the next slice): platform operators are their own accounts, not clinic users, created and disabled only by the new `support-platform-operator` command (password and authenticator set up at the terminal; [runbook](../runbooks/platform-operators.md)). They sign in at `/v1/platform/auth/*` with password and authenticator code (lockout after 5 failures, single-use codes, rotating refresh tokens) and get tokens of a separate audience and key: clinic endpoints refuse them and `/v1/platform/*` refuses clinic tokens. Only a correct authenticator code resets the failure count, and a code works once even under concurrent requests. Every console request must come from `PLATFORM_ALLOWED_CIDRS` (nobody when unset, outside tests; `*` for local development). The command also enables operators, replaces a lost authenticator, replaces a compromised password (only while the operator is disabled), and shows the QR code only once the session recording is paused. Operators can list organisations with clinic and staff counts, onboard an organisation with its first clinic and an invite link for its first clinic admin, work the doctor verification queue across organisations and verify from it (same change and `support.doctor.verified` audit entry as the support command, which is now the fallback; [runbook](../runbooks/doctor-verification.md); only the registration the operator was shown is verified, and a profile changed meanwhile is refused with 409, from the console and the command alike), and see usage per organisation (visits, signed prescriptions, payments; messages and scribe minutes stay empty until those exist). Doctor profiles record when they entered the queue. All console sign-ins, reads and changes are audited. In production the API now trusts only `TRUST_PROXY_HOPS` (default 1) proxy hops of `X-Forwarded-For` instead of every entry, and with `TRUSTED_PROXY_CIDRS` only from the load balancer's subnets. Doctor profiles' queue time moves on whenever the registration number or council changes.
