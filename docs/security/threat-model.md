# Threat Model

**Status:** Draft · **Owner:** Tech lead · **Review:** quarterly and before each new integration.

Method: list what we protect, who might attack or fail, where data crosses boundaries, and the control for each threat (STRIDE: spoofing, tampering, repudiation, information disclosure, denial of service, elevation of privilege).

## Assets
Patient identities and contact details; clinical records (notes, diagnoses, prescriptions, transcripts, audio, uploaded reports); signing authority (cloud DSC); payment status and Cashfree keys; ABDM consents and linked records; staff credentials and devices; audit log.

## Trust boundaries
1. Patient/staff device ↔ API (internet).
2. API ↔ data stores (private network).
3. API/workers ↔ third parties: Cashfree, WhatsApp provider, SMS provider, email, push (FCM/APNs), cloud DSC, drug database, speech-to-text and AI model, ABDM gateway.
4. Organisation ↔ organisation (tenant boundary inside our system).
5. Platform console ↔ clinic data (must be none for clinical content).

## Threats and controls
| # | Threat | STRIDE | Control |
|---|---|---|---|
| T1 | Staff account takeover (phished password) | S | Password + TOTP; device registration; biometric unlock; device revocation; anomaly alerts |
| T2 | Patient OTP abuse / SIM swap | S | OTP rate limits, short expiry, attempt lockout; sensitive actions need re-verification |
| T3 | Cross-tenant data access via ID guessing | I, E | Row-level security + API checks; 404 for foreign IDs; CI isolation suite |
| T4 | Public file URL leakage | I | Private buckets; signed URLs with short expiry; no PHI in file names |
| T5 | Forged payment webhook marks bill paid | T, S | Signature + timestamp verification, amount match, order status check with Cashfree |
| T6 | Duplicate webhook double-processing | T | WebhookEvent de-duplication; idempotent handlers |
| T7 | Prescription or referral letter altered after signing | T, R | Immutability, PDF hash, DSC signature, QR verification, version chain, audit log. A referral letter is insert-only (the database refuses any update or delete, by any role), its stored file is re-hashed before every download, and its QR has its own lookup table and page (`/verify/referral/<code>`), so a prescription code never vouches for a letter or the reverse. **Accepted residual:** the letter's public check shows the recipient's name, specialty and hospital (to match the paper), and a specialty or hospital (an oncologist, a psychiatric hospital) can hint at the patient's condition; accepted because only the patient's initials, age and gender are shown, no reason, notes or diagnoses, and the code (120 random bits) is only on the paper letter, so whoever can check it already holds the letter |
| T8 | Unauthorised signing | S, E | Only verified doctors; biometric/PIN approval per signature; signing events audited. Referral letters use the same PIN and its 15-minute pause after five wrong tries (one counter for prescriptions and letters), only by the referral's referring doctor, and the database checks the signer is that doctor |
| T9 | AI vendor retains or trains on data | I | DPAs with no-training clauses; approved regions; audio auto-deletion; minimum data sent |
| T10 | Prompt injection via uploaded documents into Ask AI | T, I | Ask AI read-only; answers cite sources; no tool access to write; output never auto-applied |
| T11 | Messages leak diagnosis on lock screens | I | Templates exclude diagnoses and medicine names; links require authentication |
| T12 | Malicious file upload | T | Type and size checks against the clinic's settings (`checkUpload`) and the file's first bytes, which must match the declared type (PDF, JPEG, PNG, HEIC); authentication and the role check before the body is read, then a 25 MB ceiling; one stricter per-address rate limit shared by every upload route, counted before authentication; a file whose record fails to commit is removed; a body that is not a file is 415; at most 10 results per test; files stored by a key with no patient data, written once, checked against their SHA-256 on every read; served with their stored type, `nosniff`, a sandboxing CSP and `no-store`, never to the front desk. On the web patient portal, which shows a file from a same-origin object URL (so the API's CSP does not travel with it), a file is shown in a tab only when the type received is the one the list expects and is PDF, JPEG or PNG, and it is re-typed as exactly that type; anything else (HTML, SVG, a mismatch, HEIC/HEIF) is saved as `application/octet-stream`, never rendered (`apps/web/lib/patient-files.ts`). Built for test results (API guide §3t). Still to come with the files module: malware scan before visibility |
| T13 | Lost or stolen clinic device | I | Idle lock, biometric unlock, remote revoke, encrypted local cache with limited scope |
| T14 | Insider misuse (staff browsing records) | I, R | Role-based access, chart model, audit of record views, periodic access review. Under "own patients only" an internal referral opens a chart to its receiving doctor: only the visit's own doctor can make one (after check-in), only to an active doctor of the same organisation, the access lasts only while the referral is open and never lets the receiver write the referring visit, external referrals open nothing, and every referral is audited (`referral.created` names the receiving doctor), so a referral used to hand a colleague a chart shows in the audit log |
| T15 | API abuse / denial of service | D | WAF, rate limits, autoscaling, queue back-pressure |
| T16 | Secrets leaked in code or logs | I | Secret store, scanning in CI, no PHI or secrets in logs |
| T17 | Platform staff accessing clinical data | E | Platform console has no clinical endpoints. Operators are a separate identity (not clinic users), created only by a support command, with password + authenticator, lockout, and access only from `PLATFORM_ALLOWED_CIDRS` (nobody when unset; `*`, `0.0.0.0/0` and `::/0` refused in production; the client address is taken only from trusted proxy hops, `TRUST_PROXY_HOPS`, and with `TRUSTED_PROXY_CIDRS` only from the load balancer's and the web servers' subnets; without it the API port must be reachable only from the load balancer and the web servers, or `TRUST_PROXY_HOPS=0`). The web console's session routes (`/api/platform-session/login`, `/mfa`, `/refresh` and `/logout`, which call `/v1/platform/auth/*`) reach the API from the web server, which passes on a client address only with `FORWARD_CLIENT_IP=true`, and then only the rightmost `X-Forwarded-For` entry, never entries the client wrote. Before `FORWARD_CLIENT_IP` is turned on: the load balancer in front of the web servers must overwrite `X-Forwarded-For` with, or append to it, the client address it observed, so that address is the rightmost entry; the web servers must accept traffic only from the load balancer; and the API must believe forwarded entries only from the load balancer and the web servers. The API believes them only from a peer in `TRUSTED_PROXY_CIDRS` when that is set, so list both peers there: the load balancer's subnets (the console's own requests come from the browser through it) and the web servers' subnets (the web app's session routes, clinic and console). Each adds exactly one entry, so `TRUST_PROXY_HOPS=1` fits both paths. Without `TRUSTED_PROXY_CIDRS`, set `TRUST_PROXY_HOPS=0` unless the API port can be reached only from the load balancer and the web servers. Never add the web servers' addresses to `PLATFORM_ALLOWED_CIDRS`: that would open the console's sign-in steps to anyone who can reach the web app. At sign-in only a correct authenticator code resets the failure count (reaching the limit also clears it, as it sets the lock); outside sign-in, only the operator command's `--reset-password`, `--reset-authenticator` and `--enable` reset it, each audited. A code is accepted once even under concurrent requests. Verification applies only to the registration details the operator was shown (409 if the doctor changed them meanwhile). Platform tokens have their own audience and key, so they open no clinic endpoint and clinic tokens open no console endpoint. The console's database role `dhc_platform` has no grant on any clinic table; it reads across organisations only through `SECURITY DEFINER` functions returning counts and doctors' registration details with masked contacts (ADR 0016), pinned by integration tests. System health (`GET /platform/health`) returns status and counts only: the API's version and uptime, the database's latency and latest migration name (through `platform_latest_migration()`, which leaves `_prisma_migrations` itself out of reach), and per-queue job counts, never a job's ID, name or payload, nor anything about an organisation. Successful sign-ins, wrong passwords and codes for a known operator, lockouts, refresh-token reuse and logouts, the organisation, doctor-queue, usage and system health reads (a system health view while the database is reported down may not be audited, since the entry cannot be written then; that is logged instead, as in API guide §3s), and every console change, and every refusal the console service makes (a taken slug, a verification refused or a profile changed meanwhile; requests rejected earlier by validation are not), are audited with no organisation, so one operator's activity reads in one place (`GET /platform/me` is not). A sign-in with an unknown email is audited too (`platform.auth.login.failed` with no operator), limited only by the per-address sign-in rate limit. Not audited, so that noise cannot fill the database: requests refused by the network allowlist (logged instead), an invalid or expired sign-in token at the code step (401), and a code from an operator disabled before the code step (401; one disabled during the step is audited as `platform.auth.mfa.failed`). Break-glass (if ever added) logged and time-limited |
| T18 | Data loss | D | Multi-AZ database, point-in-time recovery, monthly restore test |
| T19 | Attacker with a staff password enrols their own authenticator | S, E | Authenticators enrolled only via admin-issued invite links (single-use, 72 h, hashed, URL fragment, revocable); login never offers enrolment |
| T22 | A clinic admin takes over a staff account that also opens another clinic, via authenticator reset | E | Reset refused when the person is active staff elsewhere; those go to platform support ([runbook](../runbooks/support-authenticator-reset.md): callback plus clinic-admin confirmation, second-person approval, ticket, break-glass access), which audits the reset into every clinic the person works at (`support.authenticator.reset`) and revokes all their open links; no self-reset; reset ends every staff session and is audited (`staff.authenticator.reset`) |
| T21 | XSS steals web session tokens | S, I | Refresh token only in an httpOnly, SameSite=Strict cookie on `/api/session` (ADR 0015), and the patient portal's and platform console's in cookies of their own on `/api/patient-session` and `/api/platform-session`; the patient portal's cookie lasts only until the browser closes unless the patient opts in to 30 days on their own device, and without that the portal ends a session idle for 15 minutes across its tabs, also when a closed tab is reopened (shared computers); access token in memory, 15-minute lifetime; session routes check Origin; no third-party scripts on clinical pages |
| T23 | A forwarded message link opens a prescription or consent for someone else | I | Links are signed and short-lived; prescription and consent content needs an OTP to the patient's number or a signed-in session, never only a date of birth (Build Plan §6) |
| T24 | Patient's phone lost or shared: prescriptions or test results downloaded to it, or reports picked to upload, are read by someone else | I | Patient app keeps at most one prescription PDF and at most one test result, each in its own folder of its private cache (`prescriptions`, `test-results`); deleted when the share sheet closes (Android: as the next open of that kind starts, even if it then fails) and on sign-out or an expired session; prescription file names hold only the number and version, result names only `test-result-<n>.<ext>` (never the test). A report picked to upload is the picker's own copy (Android: `cache/DocumentPicker`; iOS: `tmp/<bundle-id>-Inbox`, with no second copy in the cache), deleted once the upload succeeds or fails, or the file is refused or unreadable; sign-out also empties both folders. Web patient portal: a file is fetched with the bearer token in the header (never in the address) and the API sends it `no-store`; a saved file is named only `<number>-v<version>.pdf` or `test-result-<n>.<ext>`; nothing is saved unasked (with pop-ups blocked the page offers a download link instead); each object URL is revoked once its tab is closed (checked every 5 seconds), 30 minutes after a file is shown, a minute after a save or a second after the fallback link is clicked, and on sign-out, idle sign-out or a session ended in another tab, which also close every tab the portal opened. A file the person downloaded stays in the browser's downloads folder, which the patient FAQ says to clear on a shared computer |
| T20 | Invite link intercepted | S | Link alone is not enough for an existing account (password + current authenticator); for a new account the admin sees acceptance in the invite list and audit log and can revoke; short expiry |
| T25 | Public doctor pages scraped, used to learn more than the doctor published, used to pass for someone else, or made unavailable | I, S, D | Shown only when the doctor listed the page and the registration is verified, the doctor and organisation are active; every other address gets the same 404 (malformed ones too), so unlisted or pending doctors cannot be told apart from missing ones. **Enumeration is intended:** the home page's directory (`public_doctor_directory()`, `GET /v1/public/doctor-directory`) lists every shown doctor in one answer, at most 500, with only fields their own pages already show (name, qualifications, specialty, organisation name, scheduled clinics' names and first address line, languages, lowest fee), never the registration, the about text, the organisation's slug, IDs or anything unlisted or unverified; the home page searches it in the browser, so typing never reaches the API. Anonymous reads run as `dhc_app` with no organisation set (no tenant row visible) through `SECURITY DEFINER` functions that return only the published columns (three for the doctor pages, the directory's second version adding only the organisation's display name; the branding ones are T26), executable by `dhc_app` only; no internal IDs, contact details, clinic phones, patients or schedules beyond which clinics and consultation types (ADR 0017), pinned by integration tests. The lastmod time is a separate `public_updated_at`, so PIN attempts (which touch `updated_at`) are never visible. A taken address is `409 slug: taken` without naming the organisation. **Impersonation:** the page shows the doctor's own name and text; only the registration number carries a "Registration number verified" badge, because that is all the platform team checks, and addresses that read like the site itself (`admin`, `app`, `clinic`, `doctor`, `platform`, `verify`, `api`, `help` and a few more) are reserved. A doctor who gives up an address frees it, and another doctor may take it: old links then open the new doctor's page (the doctor guide says so; no quarantine yet). **Scraping and availability:** 120 requests per minute per address on `/v1/public/doctors*` and `/v1/public/doctor-directory`; the home page is rendered per request but takes the directory from each web instance's fetch cache (300 seconds, kept answers served while a fresh one is fetched in the background; `PUBLIC_API_CACHE_SECONDS` cannot go below 60 outside the browser tests), waits at most 3 seconds for the API, and on a 429, failure or timeout shows "Doctor list unavailable" (only when that instance has no kept list yet) instead of failing; the hero and sign-in links render without waiting; the web page checks the address against the cached sitemap list first and answers unknown ones with a 404 without calling the single-doctor API; shown pages are cached 300 seconds by the web app (ISR) and sent `public, max-age=60, s-maxage=300`, 404s `no-store`. Each web instance is one address to the API (with its own cache), so a burst of first visits to many real pages, or direct API calls, can still use up the limit, and the pages then show "busy, try again" (nothing cached) until it resets. A CDN or WAF rate limit per client in front of the site and the API is an open item. Text the doctor typed is escaped in the JSON-LD (no `<`) and rendered as text, never HTML |
| T26 | A clinic's logo or branding used to attack visitors: script in an uploaded logo (SVG, an HTML or PDF polyglot, markup in metadata), CSS injected through the colour, a misleading, spoofed or hidden-text name, a huge or animated image, the public logo route used to read other files or another clinic's data, or one clinic's lost file taking another's logo down | T, I, S, D, E | **Logo upload** (`POST /v1/organisation-branding/logo`, clinic admins only, behind authentication before the body is read, 60 per minute per address): still PNG, JPEG or WebP only; **SVG refused** by name and by content; **animation refused** (APNG, animated WebP); the type comes from the magic numbers and must match the declared type; the whole structure is walked (PNG chunks and CRCs to IEND, JPEG segments and scans to EOI with exactly one frame header before the first scan, WebP RIFF size and chunks) and must end where the image ends, so appended payloads (ZIP, PDF, HTML: polyglots) are refused; the first kilobyte and every metadata block must hold no markup or document header (`<script`, `<html`, `<svg`, `javascript:`, `%PDF-` and others), with compressed PNG text (`zTXt`, compressed `iTXt`) inflated up to 1 MB a chunk and 4 MB a file, at most 64 text chunks, each checked as it is read and none kept (a broken stream, or more, refused) and metadata also read with NUL bytes dropped (UTF-16). **Not scanned:** image data and text in other encodings; the control for those is that the bytes are only ever served as the verified image type with `nosniff` and a sandbox policy, the scan is a second line. At most 512 KB, 4096 pixels on a side and 4 million pixels in all (decompression bombs in visitors' browsers); bodies over 1 MB are refused before they are read. Database CHECKs repeat the media types, size, hash format and that the file key is in the organisation's own folder. **Public logo route** (`GET /v1/public/logos/{sha256}`): the address is the file's SHA-256 (names no organisation, cannot be a path: 64 lowercase hex only), looked up through `public_organisation_logo` for active organisations only; when several organisations hold the same bytes each copy is tried, newest first, so a lost or damaged file of one does not take another's logo down, and a suspended organisation's copy is never used; the stored bytes are re-hashed and re-checked before they are first served (each API instance then keeps up to 64 verified logos in memory by hash, and still asks the database on every request), and a copy that fails is logged and skipped (404 when none passes); sent with the verified `Content-Type`, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; img-src 'self'; sandbox` and `Content-Disposition: inline`, from the API's origin, which takes bearer tokens and sets no cookies; `Cache-Control: public, max-age=300, s-maxage=300`, so a suspended organisation's logo stops showing within five minutes; 600 requests per minute per address. The web shows it as a plain decorative `<img>` only for an address of that shape, joined to the API's base URL (data cannot point it elsewhere). **Colour:** only `#rrggbb` is accepted (no names, functions, `var()` or `;`), and it must give white text 4.5:1 contrast (refused otherwise, so buttons stay readable); the web sets only that value as CSS variables on the branded element and re-checks it, falling back to the platform theme; no other CSS comes from data. **Text:** the display name (80) and tagline (120) refuse control, bidirectional (U+061C, U+200E–U+200F, U+202A–U+202E, U+2066–U+2069) and invisible (U+200B–U+200D, U+2060, U+FEFF) characters, in the API and in a CHECK, and are rendered as text, never HTML; the organisation's registered name stays on prescriptions, receipts and staff screens, and a doctor page's "Registration number verified" badge is unchanged, so branding cannot claim verification. The portal's sign-in shows a clinic's branding only while its clinic field holds the clinic the link named, so it never shows one clinic's look while signing in to another. Every change is audited (`organisation.branding_updated`, field names). Anonymous reads go only through definer functions that return the branding columns of active organisations (ADR 0017 addendum 2), pinned by integration tests; nothing is new to the public except what the admin chose to publish, and the home page's directory carries only the display name. Remaining: a clinic can still choose a name or logo resembling another clinic's (no review of branding; reported cases are handled by support); uploaded logos are not malware-scanned (T12; they are never served as anything but an image); and orphaned logo files are possible after a failed deletion (logged, never served, cleaned up by hand: backup and restore runbook) |
| T27 | A shared document used against a patient or a clinic: script in an uploaded sheet or report (SVG, HTML, a PDF with JavaScript, launch actions or attachments, a polyglot of PDF and HTML or an image with a payload appended), a huge image, a sheet changed after it was sent so the patient's copy no longer matches what the doctor shared, one family seeing another's documents, a withdrawn document still reachable, or file names and notes leaking into logs | T, I, S, D, E | **Upload** (`POST /v1/document-files`, doctors and clinic admins only, authenticated before the body is read, the shared 60-per-minute upload limit, 25 MB ceiling then the clinic's own `maxUploadMb`): PDF, JPEG, PNG or WebP only, the clinic's PDF, JPEG and PNG switches apply (WebP has none and is always accepted; HEIC never, browsers do not show it); **SVG and HTML refused** by name and by content. Images go through the logo checks (T26: structure walked to its end, no appended data, no markup in the head or metadata, no animation), with document limits of 10,000 pixels on a side and 50 million in all. PDFs must start with `%PDF-` at the first byte, hold no markup in the first kilobyte, and end with `%%EOF` and only whitespace after it (appended payloads refused). **PDFs are rebuilt, not vouched for:** proving an upload safe meant agreeing with every PDF reader on how the file parses, and three reviews found ways (an object stream header offset landing inside a string or comment, a duplicate object stream typed by reference, objects hidden in stream data) to hide a live `/OpenAction` script from a hand-written scanner. Instead the API keeps only the pages (`apps/api/src/modules/documents/pdf-rebuild-worker.ts`): the upload is loaded with pdf-lib, each page dictionary is cut down to what draws it (`/MediaBox` and the other boxes, `/Rotate`, `/UserUnit`, `/Resources`, `/Contents`, `/Group`; inherited resources and boxes are moved onto the page), the pages are copied into a new document and cut down again, and nothing of the upload's catalog, information dictionary or XMP metadata is copied: no `/OpenAction`, `/AA`, `/Names` (document JavaScript, embedded files), `/AcroForm` (and XFA), `/Outlines`, `/StructTreeRoot`, `/OCProperties` or `/OutputIntents`. **All annotations are dropped** (links of every kind, form fields with their values, stamps, comments), as are page `/AA`, thumbnails and page metadata: simpler and safer than telling a safe link from an unsafe action. Objects the new pages do not reach are dropped; every object left is walked without recursion, and any of `/JS`, `/JavaScript`, `/Launch`, `/EmbeddedFile(s)`, `/RichMedia`, `/XFA`, `/GoToR`, `/GoToE`, `/SubmitForm`, `/ImportData`, `/AA`, `/OpenAction`, `/URI`, `/URL` and `/Metadata`, as a key, as a value or as an object of its own (`/S 6 0 R` with `6 0 obj /Launch`), escapes decoded, is removed or nulled, so a script, link or XMP packet the pages reach through their resources is neutered; stream dictionaries lose `/F`, `/FFilter`, `/FDecodeParms` (data in another file or at a URL) and `/Ref` (another file's page in a form); an object pdf-lib could not parse (which it would write back byte for byte) becomes `null`; a stream with no usable filter (none, `[]`, `null`, anything but names) is Flate-compressed, so no text of the upload (an object hidden in a page's content) is left in plain view. The output is written by pdf-lib with object streams off (one classic cross-reference table, every object in plain view, no dates, so the same upload gives the same bytes for a given pdf-lib, Node and zlib version), refused as `too_large` when it is over the clinic's limit or 25 MB (writing object streams out can make a file several times larger), and checked before it is kept (`pdf-scan.ts`, which only ever sees our own output): header, objects in plain PDF syntax at most 100 deep, stream data of exactly its direct `/Length` with no `n g obj` header in it and no stream pointing at another file, a table listing exactly those objects at their offsets, a trailer with no `/Encrypt` or `/Prev`, no object or cross-reference streams, and none of the names above. **Only the rebuilt file is stored, hashed and served**; the audit entry also records the upload's own size and SHA-256 (`originalSizeBytes`, `originalSha256`). **Bounded work:** pdf-lib parses synchronously, keeps every object in memory and pools every distinct name for the life of its thread, so the rebuild runs in a fresh worker thread per file (`pdf-rebuild.ts`): `resourceLimits` of 128 MB old generation and 16 MB young, and because a process-wide `--max-old-space-size` (in `NODE_OPTIONS`) silently overrides those, the worker's heap is also polled every 20 ms and the worker ended past the same limit; a 5-second wall-clock limit after which the worker is terminated, its slot handed on only once it has exited; at most 500 pages (refused as `too_many_pages`, also when the page tree's `/Count` claims more); and one budget of 128 MB for everything pdf-lib's stream decoders produce in that worker, across all streams and filter stages, with at most 4 filters per stream (decoded buffers live outside the capped heap; the patch on pdf-lib's decoders checks itself, and a pdf-lib it cannot cap makes the rebuild report itself broken rather than run uncapped). A timeout or out-of-memory end is the upload's fault (`not_a_document`, logged with the reason, never the file); a worker that cannot start or fails otherwise is ours (503 `file: unavailable`, logged as an error), and the API rebuilds a sample PDF at start-up and logs an error when that fails. **Memory and fairness:** one worker adds up to about 350 MB to the API process at worst (measured: one hostile file, 350 MB peak process RSS; two at once 560 MB), so rebuilds run **one at a time** by default (`PDF_REBUILD_CONCURRENCY`, 1 to 4; the container needs 1 GB plus 400 MB for each further one, runbook `deploy.md`). At most twice that many wait, each for at most 10 seconds, a waiting upload whose request closes leaves the queue (a running one has its worker ended), and an organisation has at most two rebuilds running or waiting, so one account sending hostile files holds at most one slot and one place in the queue; anything beyond is 503 `file: busy` with `Retry-After: 60`. Ten parallel hostile uploads from one clinic: one runs, one waits, eight are turned away at once; peak RSS 276 MB. A cross-reference stream claiming two billion entries, an object stream header bomb, a 1 GB object stream zip bomb, pages behind a stream that inflates past the budget or behind five filters, nesting 100,000 deep and 24 MB of long names all end within the limits (unit tests in `pdf-rebuild.test.ts`, built from `pdf-attack-samples.ts`). **Encrypted PDFs** are refused with their own reason (`encrypted`). **Accepted loss:** links, form fields and their filled-in values, bookmarks, attachments, comments and accessibility tags of uploaded PDFs are removed (the guides say so; print a filled form to PDF first). PNG text chunks are inflated within 1 MB each and 4 MB per file, at most 64 of them, checked as they are read and never kept (T26), so a small upload cannot make the server inflate and hold hundreds of megabytes. **Where the checks matter most:** the API serves files with their verified type, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; img-src 'self'; sandbox`, `Cache-Control: no-store` and a name with no patient data (`document-<id>.<ext>`), but the web app (portal and clinic) fetches the file with the bearer token and opens it from a `blob:` URL, which carries none of those headers. On that path the server's control is what it stores: images that passed the checks above and PDFs it wrote itself. The remaining risk is the browser's own PDF and image viewers rendering page content (content streams, fonts and images inside a PDF are copied as they are; image pixels are not decoded), which run no page script from a blob of type `application/pdf` or `image/*`. **Not checked:** what page content draws, and image pixels. **Storage:** by key in the organisation's own folder (a CHECK), no patient data, title or file name in the key, written once, re-hashed (SHA-256) before every download; file rows never change (trigger), a file whose row fails to commit is removed. **Immutability:** a share copies the sheet's title, category and language and points at the exact file row it was made with; renaming, replacing or archiving the sheet never changes it, and the database refuses any change to a share but its first opening and its withdrawal, each recorded once, and any delete. **Access:** shares only by doctors under the chart model; the front desk and clinic admins never see shared documents; the portal shows only the account's family's (and their merged records'), not withdrawn, after the consents, 404 otherwise; a fresh upload is usable once, by its uploader, within 24 hours, so an upload ID cannot be borrowed by another user or clinic. **Logs:** the audit log holds IDs, media types, sizes and hashes only, never titles, notes or file names; titles and notes travel only in JSON bodies, never in URLs. Remaining: opening files in the web app through a short-lived signed same-origin URL that keeps the server's headers, instead of a `blob:` URL (open item below); no malware scanning yet (open item below, with T12 and T26); an unused upload stays stored (no clean-up job yet); a doctor can still share the wrong patient's report (the dialog names the patient, and withdrawal is the remedy) |

## Open items
- [ ] CDN or WAF rate limiting per client in front of the public website and the API before launch, for scraping and for availability: the API's limit on `/v1/public/doctors*` sees the web server's address for server-rendered pages, so one busy client can make the pages show "busy" for everyone (T25).
- [ ] Malware scanning of uploaded files (test results, clinic logos and shared documents today) before they become visible (T12, T26, T27).
- [ ] Clean-up of document uploads never used for a sheet or a share (stored, never served; T27).
- [ ] Open shared documents in the web app from a short-lived signed same-origin URL that keeps the API's `nosniff` and sandbox headers, rather than a `blob:` URL that carries none (T27; the portal's file registry would hand out the URL instead of a blob).
- [ ] Pen-test scope agreed (web, both apps, API, tenant isolation, payment and webhook flows).
- [ ] Vendor security reviews for DSC, AI and WhatsApp providers.
