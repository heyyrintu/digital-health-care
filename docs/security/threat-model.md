# Threat Model

**Status:** Draft · **Owner:** Tech lead · **Review:** quarterly and before each new integration.

Method: list what we protect, who might attack or fail, where data crosses boundaries, and the control for each threat (STRIDE: spoofing, tampering, repudiation, information disclosure, denial of service, elevation of privilege).

## Assets
Patient identities and contact details; clinical records (notes, diagnoses, prescriptions, transcripts, audio, uploaded reports); signing authority (cloud DSC); payment status and Cashfree keys; ABDM consents and linked records; staff credentials and devices; audit log.

## Trust boundaries
1. Patient/staff device ↔ API (internet).
2. API ↔ data stores (private network).
3. API/workers ↔ third parties: Cashfree, WhatsApp provider, SMS provider, email, push (FCM/APNs), cloud DSC, drug database, speech-to-text and AI model, ABDM gateway.
4. Organisation ↔ organisation (tenant boundary inside our system).
5. Platform console ↔ clinic data (must be none for clinical content).

## Threats and controls
| # | Threat | STRIDE | Control |
|---|---|---|---|
| T1 | Staff account takeover (phished password) | S | Password + TOTP; 5 wrong passwords or codes lock the account for 15 minutes, and only a correct authenticator code resets the count, so a known password does not buy unlimited code guesses across sign-ins; a code is accepted once even under concurrent requests, and never once the account was disabled, locked or had its authenticator reset after the code was checked (`auth.mfa.failed` with `code_reused` or `changed_meanwhile`); device registration; biometric unlock; device revocation; anomaly alerts |
| T2 | Patient OTP abuse / SIM swap | S | OTP rate limits, short expiry, attempt lockout; sensitive actions need re-verification |
| T3 | Cross-tenant data access via ID guessing | I, E | Row-level security + API checks; 404 for foreign IDs; CI isolation suite |
| T4 | Public file URL leakage | I | Private buckets; signed URLs with short expiry; no PHI in file names |
| T5 | Forged payment webhook marks bill paid | T, S | Signature + timestamp verification, amount match, order status check with Cashfree |
| T6 | Duplicate webhook double-processing | T | WebhookEvent de-duplication; idempotent handlers |
| T7 | Prescription altered after signing | T, R | Immutability, PDF hash, DSC signature, QR verification, version chain, audit log |
| T8 | Unauthorised signing | S, E | Only verified doctors; biometric/PIN approval per signature; signing events audited |
| T9 | AI vendor retains or trains on data | I | DPAs with no-training clauses; approved regions; audio auto-deletion; minimum data sent |
| T10 | Prompt injection via uploaded documents into Ask AI | T, I | Ask AI read-only; answers cite sources; no tool access to write; output never auto-applied |
| T11 | Messages leak diagnosis on lock screens | I | Templates exclude diagnoses and medicine names; links require authentication |
| T12 | Malicious file upload | T | Type and size checks; malware scan before visibility |
| T13 | Lost or stolen clinic device | I | Idle lock, biometric unlock, remote revoke, encrypted local cache with limited scope |
| T14 | Insider misuse (staff browsing records) | I, R | Role-based access, chart model, audit of record views, periodic access review |
| T15 | API abuse / denial of service | D | WAF, rate limits, autoscaling, queue back-pressure |
| T16 | Secrets leaked in code or logs | I | Secret store, scanning in CI, no PHI or secrets in logs |
| T17 | Platform staff accessing clinical data | E | Platform console has no clinical endpoints. Operators are a separate identity (not clinic users), created only by a support command, with password + authenticator, lockout, and access only from `PLATFORM_ALLOWED_CIDRS` (nobody when unset; `*`, `0.0.0.0/0` and `::/0` refused in production; the client address is taken only from trusted proxy hops, `TRUST_PROXY_HOPS`, and with `TRUSTED_PROXY_CIDRS` only from the load balancer's and the web servers' subnets; without it the API port must be reachable only from the load balancer and the web servers, or `TRUST_PROXY_HOPS=0`). The web console's session routes (`/api/platform-session/login`, `/mfa`, `/refresh` and `/logout`, which call `/v1/platform/auth/*`) reach the API from the web server, which passes on a client address only with `FORWARD_CLIENT_IP=true`, and then only the rightmost `X-Forwarded-For` entry, never entries the client wrote. Before `FORWARD_CLIENT_IP` is turned on: the load balancer in front of the web servers must overwrite `X-Forwarded-For` with, or append to it, the client address it observed, so that address is the rightmost entry; the web servers must accept traffic only from the load balancer; and the API must believe forwarded entries only from the load balancer and the web servers. The API believes them only from a peer in `TRUSTED_PROXY_CIDRS` when that is set, so list both peers there: the load balancer's subnets (the console's own requests come from the browser through it) and the web servers' subnets (the web app's session routes, clinic and console). Each adds exactly one entry, so `TRUST_PROXY_HOPS=1` fits both paths. Without `TRUSTED_PROXY_CIDRS`, set `TRUST_PROXY_HOPS=0` unless the API port can be reached only from the load balancer and the web servers. Never add the web servers' addresses to `PLATFORM_ALLOWED_CIDRS`: that would open the console's sign-in steps to anyone who can reach the web app. At sign-in only a correct authenticator code resets the failure count (reaching the limit also clears it, as it sets the lock); outside sign-in, only the operator command's `--reset-password`, `--reset-authenticator` and `--enable` reset it, each audited. A code is accepted once even under concurrent requests. Verification applies only to the registration details the operator was shown (409 if the doctor changed them meanwhile). Platform tokens have their own audience and key, so they open no clinic endpoint and clinic tokens open no console endpoint. The console's database role `dhc_platform` has no grant on any clinic table; it reads across organisations only through `SECURITY DEFINER` functions returning counts and doctors' registration details with masked contacts (ADR 0016), pinned by integration tests. Successful sign-ins, wrong passwords and codes for a known operator, lockouts, refresh-token reuse and logouts, the organisation, doctor-queue and usage reads, and every console change, and every refusal the console service makes (a taken slug, a verification refused or a profile changed meanwhile; requests rejected earlier by validation are not), are audited with no organisation, so one operator's activity reads in one place (`GET /platform/me` is not). A sign-in with an unknown email is audited too (`platform.auth.login.failed` with no operator), limited only by the per-address sign-in rate limit. Not audited, so that noise cannot fill the database: requests refused by the network allowlist (logged instead), an invalid or expired sign-in token at the code step (401), and a code from an operator disabled before the code step (401; one disabled during the step is audited as `platform.auth.mfa.failed`). Break-glass (if ever added) logged and time-limited |
| T18 | Data loss | D | Multi-AZ database, point-in-time recovery, monthly restore test |
| T19 | Attacker with a staff password enrols their own authenticator | S, E | Authenticators enrolled only via admin-issued invite links (single-use, 72 h, hashed, URL fragment, revocable); login never offers enrolment |
| T22 | A clinic admin takes over a staff account that also opens another clinic, via authenticator reset | E | Reset refused when the person is active staff elsewhere; those go to platform support ([runbook](../runbooks/support-authenticator-reset.md): callback plus clinic-admin confirmation, second-person approval, ticket, break-glass access), which audits the reset into every clinic the person works at (`support.authenticator.reset`) and revokes all their open links; no self-reset; reset ends every staff session and is audited (`staff.authenticator.reset`) |
| T21 | XSS steals web session tokens | S, I | Refresh token only in an httpOnly, SameSite=Strict cookie on `/api/session` (ADR 0015); access token in memory, 15-minute lifetime; session routes check Origin; no third-party scripts on clinical pages |
| T23 | A forwarded message link opens a prescription or consent for someone else | I | Links are signed and short-lived; prescription and consent content needs an OTP to the patient's number or a signed-in session, never only a date of birth (Build Plan §6) |
| T24 | Patient's phone lost or shared: prescriptions downloaded to it are read by someone else | I | Patient app keeps at most one prescription PDF, only in its cache; deleted when the share sheet closes (Android: on the next open) and on sign-out or an expired session; file names hold only the prescription number and version |
| T20 | Invite link intercepted | S | Link alone is not enough for an existing account (password + current authenticator); for a new account the admin sees acceptance in the invite list and audit log and can revoke; short expiry |
